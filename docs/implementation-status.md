# ArchiCraft implementation status

_Gap analysis of the codebase against docs/SRS.md (567 requirements), generated 2026-10-17. Status values: **done** (every clause verified in code), **partial** (substantive behaviour exists, at least one clause missing), **missing** (nothing substantive). Remaining effort: S/M/L/XL. Since 2026-10-21 the per-requirement rows live in [docs/status/requirements.json](status/requirements.json), and since 2026-11-10 only there: `python3 scripts/status.py report` prints the counts by status and priority, the per-section table and the requirement table, `python3 scripts/status.py show <ID>` the row of one requirement, and the dashboard's roadmap page (`scripts/dashboard.py`) shows the counts and their history; CI checks the rows (docs/testing.md, "Implementation status"). This document keeps no generated table, so a pull request that changes a status edits only the JSON. The narrative sections are the analysis of 2026-10-17 and are edited by hand._

## Summary

Increment 0 (the walking skeleton of Appendix F) is delivered: a four-crate Rust workspace with a command/undo core where every mutation is a serialisable, invertible `Command`; storeys, layers and 25 default materials; straight walls (single/chain/rectangle, L and T junctions) and slabs with holes; a plan view (cut, projected and overhead classes with merged cut fills) and a wgpu 3D view; snapping, angle constraint and typed polar input; an `ifcx_alpha` writer and lenient reader with the full spatial tree, closed meshes, materials, in-file `archicraft::` schema declarations, golden files and a CI conformance run against buildingSMART's ifcx-core and viewer; atomic save with backups, background autosave with crash recovery, local crash reports and preferences. Its exit criterion (a storey with walls and a slab round-trips through IFCX and passes IFX-006 in CI) is met. On 2026-10-17, of the 567 requirements, 68 were done, 155 partial and 344 missing; of the 314 Must requirements, 61 were done, 115 partial and 138 missing (`python3 scripts/status.py report` gives the current counts). What comes next is increment 1 (core modeller): the editing area (EDT) has no user-facing command at all, layer structures/profiles (PRF), columns, beams, openings, doors and windows do not exist, and the priority-based junction engine needed for fixtures F2/F6/F7 is absent. Before those element kinds are added, two structural decisions pay off across every later increment: making the element kind, IFC class and tool/default/counter tables extensible instead of closed enums matched in ~15 places (since largely resolved by the kind registry, see Technical debt), and adding the relation store (host, solid operation, annotation binding) and an incremental geometry evaluation that Appendix F increments 1 to 3 all rely on.

## Architecture summary

**archicraft-model** — the headless domain model (no UI, geometry or file-format dependency). `Project` aggregates info, settings (units, cut plane, tessellation), site/building, a sorted `StoreyList`, flat `Vec<Layer>`/`Vec<Material>`, an `IndexMap<ElementId, Element>`, tool defaults, 3D views and name counters. `Element` is a flat envelope (id, name, home storey, layer, IFC class, position, locked) around an `ElementKind` payload generated by the kind registry (`Kind` trait and `kinds!` list in `kinds/`, one module per kind: wall, slab and the test-only dummy and note kinds); walls store a reference line plus thickness/offsets/`TopLink`, slabs a CCW outline with CW holes. Every change is a `Command` (24 variants) planned into primitive invertible `Edit`s applied by `History` with bounded undo/redo, journal and replay; `validate.rs` is the single gate for element validity; `units.rs` parses and formats lengths/angles; `template.rs` is the hard-coded default metric template; `samples.rs` builds the reference models.

**archicraft-geometry** — turns the model into closed, outward-oriented `TriMesh` bodies in storey-local coordinates: `wall::footprints` resolves L and T junctions from reference-line contact (3+ walls, crossings and priorities deferred), `extrude` builds prisms with spade CDT caps, `ModelGeometry::evaluate_incremental` evaluates again, inside `catch_unwind`, only the elements an edit dirtied (`dirty::dirty_set`: change-log stamps, moved storeys, wall contact through the per-storey R-tree, relation dependents) through the per-kind generators of `kinds/` (`GeometryKind`, one module plus one registry line per kind; compound parts as `ElementGeometry::children`), `ModelGeometry::evaluate` being the same path from an empty geometry, `slice.rs` cuts horizontally into geo polygons and `plan.rs` classifies parts into cut/projected/overhead, merges same-material cut regions and offers picking. No Boolean engine, no arbitrary-plane slicing.

**archicraft-ifcx** — the `ifcx_alpha` adapter: `writer.rs` emits the spatial tree with bsi::ifc classes, names, storey transforms, mesh bodies inheriting material nodes, wall axes and the `archicraft::` parametric data declared in-file by `schema.rs` (FORMAT_VERSION 2, which added spaces; `migrate.rs` upgrades format 1 files); `reader.rs` restores an editable project leniently with a problem report and flags newer formats; `validate.rs` mirrors the reference implementation offline with D.9 limits; `json.rs` guarantees deterministic plain-decimal output; `registry.rs` bundles the four buildingSMART schemas. Third-party files are rejected, nothing foreign is preserved.

**archicraft-app** — eframe/egui 0.36.2 with egui_tiles tabs and a wgpu offscreen 3D renderer. `Workspace` holds the `Document` (project + history + cached geometry/plans), preferences, the `ToolState` state machine, the global selection and per-view states; panels only mutate through `Workspace::execute(Command)`. `views/plan.rs` paints the plan with the egui painter and hosts the inlined point-input pipeline (typed value → Shift constraint → snap); `views/view3d.rs` navigates, picks and caches a `GpuScene` keyed by revision and selection; `commands/` holds the command registry (33 commands, 23 with a default shortcut) from which the menu bar is built; `ui/` holds the menus, toolbox, status bar, properties strip/settings dialog, project browser and dialogs; `persistence/` provides atomic save with backups, locked-session autosave with recovery, crash reports and JSON preferences.

### Extension points

- Add a menu command (UI-017): one `CommandSpec` in crates/archicraft-app/src/commands/<area>.rs (id, `.menu(path, group, order)`, optional `.bind(...)` and `.scope(...)`, `enabled_when`/`checked_when`/`dynamic_label` on `CommandCtx`, handler) plus its two catalogue keys `cmd-<id>-label` and `cmd-<id>-desc` in locales/en/commands.ftl, its id in the pinned list of commands/tests.rs and its place in the expected menu contents of `menus_follow_group_and_order` (commands/tests.rs), which pins every menu's entries, order and separators. The menu bar is built from the menu places (`Registry::menu`), so ui/shell.rs does not change: the command appears in its menu at its group (separators between groups) and order, with its shortcut, enabled state, check box and dynamic label; a path such as `view/zoom` makes a submenu, which needs a title arm in `commands::menu_title` and a `menu-view-zoom` key in locales/en/app.ftl. Menus, shortcuts, the toolbox and the status bar run commands through `ArchiCraftApp::invoke`; a toolbox or status-bar button names its command by a constant of the command module (for example `commands::view::FIT_WINDOW`), never by a literal id in shell.rs.
- Add an element kind (e.g. Column), step by step: (1) crates/archicraft-model/src/kinds/: a new module `column.rs` with the parameter payload (`pub struct Column {...}`: plan geometry in metres, a `VerticalLink` for base and top (ELM-006), material) and `impl Kind for Column`: its `KindDescriptor` (`label_key`/`noun_key`, `node_prefix`, `code`, `name_prefix` e.g. "C", `default_class` and `ifc_classes` (`IfcClass` variants and codes in element.rs if needed), `predefined_types`, `has_tool`, `template_defaults`, and `fields`, its parameters as FieldSpecs with getters and setters, crates/archicraft-model/src/fields.rs) and the hooks `material`/`set_material`, `validate`, `transform`, `vertical_extent`, `rehome` and `plan_bounds`, overriding `storey_links`, `relative_top` (a top linked relative to the home storey, which `RelationStore::moved_by_storeys` finds through it), `relink`, `unlink_storey`, `fix_top`, `parts`, `container` or `plan_measure` (the length or area the properties panel shows) where the defaults do not fit. (2) One line in the `kinds!` invocation (crates/archicraft-model/src/kinds/mod.rs:381): it generates the `ElementKind` and `KindTag` variants, `KINDS`, `Element::as_column()` and the delegating methods. Project queries, validation, commands, the name counters (`NameCounters`, keyed by `KindTag`) and the tool-defaults slots (`ToolDefaults`, filled from `template_defaults`) go through the descriptor and the hooks and need no change; the test-only `dummy` kind (kinds/dummy.rs) shows the minimum. (3) The keys `model-kind-column` and `model-kind-column-noun` in crates/archicraft-app/locales/en/model.ftl. (4) crates/archicraft-geometry/src/kinds/: a new module `column.rs` with `impl GeometryKind for Column` (the trait, crates/archicraft-geometry/src/kinds/mod.rs:72): `evaluate` produces `ElementGeometry {parts, axis, children}` from an `EvalContext` (reuse `extrude`; one `PartGeometry` per entry of `Kind::parts`, by role, for a compound kind), and `local_extent` is overridden only if stored offsets must stay exact; plus one line in the `generators!` invocation (kinds/mod.rs:117) and a sample element in `sample_elements` of crates/archicraft-geometry/tests/kinds.rs. Without the line the kind is listed as `UnsupportedKind` and the registry test fails. evaluate.rs stays generic: neighbour data such as wall junctions is resolved there before the generators run and handed in through `EvalContext`; if the kind joins walls, extend wall.rs. (5) crates/archicraft-geometry/src/plan.rs only if it needs a non-body plan symbol (bodies are sliced generically). (6) crates/archicraft-ifcx/src/alpha/schema.rs: `pub const COLUMN = "archicraft::column"`, its code in `KINDS`, its object schema in `declarations` and, with a tool, its defaults in `toolDefaults` of `project` (the `counters` schema follows `KindTag::ALL`); writer.rs arms in `element_attributes` (without one the element is reported as not storable) and `tool_defaults`; reader.rs arms in `read_element` and `read_defaults_slot`. The declarations are embedded in every file, so the golden files change; bump `FORMAT_VERSION` and add a step to `MIGRATIONS` (alpha/migrate.rs) if the change is not backwards tolerant (see the item below on reader-visible shapes). A new stored kind sets `KindCodec::SINCE_FORMAT` to the format that first stores it (as alpha/kinds/space.rs does with 2), so that reading a file of an earlier format takes the template's defaults slot and counts the elements without reporting them as missing; its step in `MIGRATIONS` changes nothing and makes readers of the older format flag the new files as newer. ## Technical debt

- Plan view ignores elements from other storeys: `plan_drawing` (crates/archicraft-geometry/src/plan.rs:120) iterates only `project.elements_on(storey)`, so a wall on the storey below that reaches into this storey's view range (or a slab linked to the storey above) is never shown or cut; VIEW-010's view range is only partially honoured.
- Wall junctions limited to L and T: crates/archicraft-geometry/src/wall.rs:14-16 (module doc) and :227-231 (`resolve_end`) leave 3+ walls at a node, crossings, collinear continuations and all priority/layer-based joins (WAL-020..027) square; material `priority` (`Material::priority`, crates/archicraft-model/src/material.rs:155) is stored and edited but never used.
- All fill patterns render as solid tones: `FillPattern` (crates/archicraft-model/src/material.rs:95) and `draw_plan` (crates/archicraft-app/src/views/plan.rs:454-472) draw `cut_fill.foreground` as a flat egui Mesh; `FillPattern` variants and `CutFill.background` have no visual effect (DSP-009/010).
- Hover highlighting in 3D is dead code: `view3d::ui` (crates/archicraft-app/src/views/view3d.rs:206) calls `build_scene(..., None)` and `SceneKey` (crates/archicraft-app/src/workspace.rs:94) omits hover, so the HOVER_TINT path in crates/archicraft-app/src/views/render3d.rs:129-144 never runs.
- Whole-model re-evaluation on every edit in the application: `Document::geometry` (crates/archicraft-app/src/document.rs:113) re-runs `ModelGeometry::evaluate` for all elements and clears all plan caches when `revision` changes, although `ModelGeometry::evaluate_incremental` (crates/archicraft-geometry/src/evaluate.rs:177) evaluates again only what the edits dirtied and lists the changed elements and storeys. Will not meet NFR-PERF targets for RM-L until the plan and 3D caches follow those (archicraft-5a64).
