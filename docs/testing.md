# Testing

How ArchiCraft is tested and which check keeps each done requirement done. This file is the
skeleton of the regression net (epic `regression-and-status`, docs/roadmap.md); the tasks of
that epic fill in their sections. The commands to run are in the README and in CLAUDE.md.

## Golden files and ARCHICRAFT_BLESS

The IFCX writer's output is pinned by golden files in `crates/archicraft-ifcx/tests/golden/`,
compared byte for byte by `cargo test -p archicraft-ifcx --test roundtrip`. Each golden file is
the output of a sample of `archicraft_model::samples::catalogue()` (NFR-MNT-003):
`catalogue_samples_reproduce_the_golden_files` builds every sample, saves it with its golden
file's header options and compares bytes, and `golden_files_are_reproduced` opens and saves
every golden file. The samples are built with the seeded `FixtureBuilder` (below), so their
identities, and the files of the `reference_models` example, are the same on every run. They
change only for an intended format change: on a bead labelled `format-change`, regenerate them
with

```sh
ARCHICRAFT_BLESS=1 cargo test -p archicraft-ifcx --test roundtrip
```

and review the text diff; the blessing writes catalogue goldens from the samples. Adding a
sample is one line in the catalogue (`samples.rs`, `CATALOGUE`) plus the blessing, which creates
its golden file. `.gitattributes` marks `*.ifcx` as `-text`, so no checkout converts
their line endings (NFR-PORT-004); they still diff as text.

The damaged files in `crates/archicraft-ifcx/tests/corrupt/` (PRJ-008) are the walls-and-slab
golden file with one kind of damage each, generated by `corrupt_fixtures_are_reproduced`. After
an intended format change, regenerate them the same way:

```sh
ARCHICRAFT_BLESS=1 cargo test -p archicraft-ifcx --test corrupt
```

The files in `crates/archicraft-ifcx/tests/formats/` are not golden files: each is a copy of a
golden file as an earlier format version wrote it (`format-1.ifcx`: two-storey-shell at
FORMAT_VERSION 1), and every later release must keep loading it without problems
(`cargo test -p archicraft-ifcx --test formats`, IFX-090, IFX-091). They are frozen: no bless
loop writes them, and `frozen_format_fixtures_never_change` fails with “frozen format fixture
changed” when their bytes change. A format bump adds a new frozen file and a migration step
(crates/archicraft-ifcx/src/alpha/migrate.rs); it never regenerates an old one.

A successor IFCX version plugs into the adapter table without touching the model or geometry
crates (IFX-091, NFR-MNT-004). The cargo feature `successor-stub` of `archicraft-ifcx` adds a
mock successor, `ifcx_successor_mock`, and `tests/successor.rs` checks that a golden file
relabelled as that version routes to it and loads to the same project, that unknown versions
still fail naming every supported one and that saving writes `ifcx_alpha`:

```sh
cargo test -p archicraft-ifcx --features successor-stub --test successor
```

Without the feature the same file only checks that the stub stays out of the default build.
The CI job Test runs the crate's tests and clippy with the feature (`.github/workflows/ci.yml`).
[docs/ifcx-evolution.md](ifcx-evolution.md) is the runbook for adopting a real successor.

`tests/schema_publication.rs` prepares publishing the `archicraft::` schema (IFX-092): it
replaces the in-file `archicraft::` schemas of each golden file in memory with an import of the
schema-only document that the example `archicraft_schema` writes, and checks with
`validate::validate_with` that the file still validates. The golden files on disk stay unchanged.

Blessing never happens to get a test green. The gate refuses golden-file edits on beads without
the `format-change` label, and the pull request shows the regenerated files' diff next to the
code that changed them; the reviewer checks that every changed byte follows from the intended
change. Because the golden files are single-line compact JSON, read that diff through the review
view snapshots below.

## Seeded fixtures and stand-ins

`archicraft_model::samples::FixtureBuilder` builds reproducible projects through commands:
`FixtureBuilder::new(name)` starts from the default template with version 5 UUIDs under
`FIXTURE_NAMESPACE` from `<name>/<role>/<n>` (`template::default_metric_project_with` takes the
identity source), `storey(index)`, `element(storey, kind)` for any registered kind, the
`wall`/`slab` shorthands and `edit` create or change elements with ids from
`<name>/<kind code>/<n>`, and `finish()` returns the project. Elements are added with one
`AddElements` per batch. Two builds of the same fixture are equal, every identity included
(IFX-010, IFX-011).

`samples::stand_in(n)` is a synthetic stand-in for RM-M and RM-L (SRS 7.3) with exactly `n`
elements, for the NFR-PERF-006 and VIEW-001 budgets until the reference models exist:
five 3.0 m storeys per block of 4 m rooms with an exterior wall ring (L corners), interior
walls in T junctions and one slab per storey, further blocks along +X beyond 5,000 elements,
padded with free-standing 1 m stubs. `STAND_IN_SIZES` lists 1,000, 5,000 and 20,000. They are
checked by `cargo test -p archicraft-model --test samples` (exact counts, determinism, all
three sizes), `-p archicraft-geometry --test stand_ins` (no evaluation problems, L and T
junctions on every storey) and `-p archicraft-ifcx --test roundtrip` (`stand_in(1_000)` round
trip; the 5,000 case is `#[ignore]`d, about 0.4 s in the dev profile).

## Determinism and rounding (IFX-007)

`crates/archicraft-ifcx/tests/determinism.rs` holds IFX-007's checks: two saves differ only in
`header.timestamp` and `header.dataVersion`, save-load-save is byte-identical for awkward floats
(`0.1 + 0.2`, `1/3`, `1e-7`, `12345.678901234`), no output, compact or indented, contains an
exponent, `data[]` follows the spatial tree (project, site, building, each storey in elevation
order with its elements and their sub-nodes, then materials), key order is stable, and indented
output loads to the same project and saves back to the golden bytes.

The reading of "coordinates are rounded to 10⁻⁶ m" these tests pin: it covers the coordinates
in the standard namespaces, which other IFCX consumers read, namely mesh points, curve points
(the wall `Axis`) and the translation of every `usd::xformop` placement (the storey elevation
today). Parameters in the `archicraft::` namespace, plan coordinates such as wall start and end
or slab outlines included, are written at shortest round-trip precision and load back bit for
bit (NFR-ACC-002, NFR-ACC-001). A storey at 2.9999999999 m is therefore placed at `3` and keeps
`2.9999999999` in `archicraft::storey`; exported points stay within 0.1 mm of the model
(IFX-031). Should the product owner decide that plan coordinates must be rounded too, the
consistent change is to snap model coordinates to 10⁻⁶ m when commands are validated, which
changes NFR-ACC-002's "never rounded".

## Snapshots

`.gitattributes` keeps `*.snap` files at LF on every checkout, so snapshots compare equal on
Windows.

**IFCX review view.** `review_view_snapshots` in `crates/archicraft-ifcx/tests/determinism.rs`
writes an insta snapshot of each sample's golden file, saved again by the current writer, into
`crates/archicraft-ifcx/tests/snapshots/`. The snapshot is the document indented, with every
mesh's `points` and `faceVertexIndices` and every curve's `points` replaced by
`{"count": n, "fnv": "…"}`, the FNV-1a hash of the rounded values as written. A parameter change
is then a one-line hunk, and a changed body shows as a changed hash. CI sets `CI=true`, which
makes insta fail on any mismatch instead of writing a new snapshot.

After an intended change of the output, review and accept the new snapshots with

```sh
cargo insta test -p archicraft-ifcx --test determinism --review
```

(`cargo install cargo-insta`; without it, `INSTA_UPDATE=always cargo test -p archicraft-ifcx
--test determinism` writes them, and `git diff` shows the change). Never accept a snapshot whose
diff you have not read.

**In the pull request.** Both diffs, the golden files' and the snapshots', are part of the pull
request and are reviewed there: the PR template has a checkbox for it. A pull request that
changes the output without a matching snapshot diff fails CI.

## Conformance

`conformance/run.sh` checks IFCX files against buildingSMART's reference code at the pinned
commit (IFX-006) in three steps per file: (a) the reference implementation loads it with schema
validation, (b1) the viewer's composition gives the expected spatial tree in Node, and (b2) the
viewer itself, in headless Chromium driven by Playwright, shows that tree, renders geometry and
every material colour. CI runs it on the reference models and the golden files and uploads one
viewer screenshot per file for the manual release check. `conformance/README.md` describes the
steps. Its build output (`.ifc5/`, `node_modules/`, `.build/`, and the Playwright
`test-results/` and `playwright-report/`) is ignored by `conformance/.gitignore`, so a local
run leaves `git status` clean.

**On every platform.** The CI job runs on Linux for every pull request and every push to
`main`. The conformance matrix (`.github/workflows/conformance-matrix.yml`) runs the same check
on Linux, Windows (Git Bash) and macOS nightly and by hand, and on Linux alone for every pull
request that changes `crates/archicraft-model`, `crates/archicraft-geometry`,
`crates/archicraft-ifcx`, `conformance/` or the workflow itself (no Windows or macOS job runs
on a pull request, docs/loop.md); a docs-only pull request does not start it, and none of its
jobs is a required check. Its last job, "Same PASS lines on every OS", runs a negative
self-test of the comparison and, except on pull requests, fails unless the runs print the same
`PASS` lines (`conformance/compare-runs.sh`, compared as sorted sets) and none prints `FAIL`.
Each OS uploads its screenshots as `viewer-screenshots-<OS>`.

**Release checklist.** The checks that run by hand once per release, the hosted IFC5 viewer of
IFX-006 (b) above all, are in [docs/test-plan/release-checklist.md](test-plan/release-checklist.md).

## Fixture registry

`crates/archicraft-model/src/fixtures.rs` is the registry of the geometry fixtures of SRS
Appendix D.7 (`D7`, F1..F9) and of further named cases (`EXTRA`). It lives in `src`, not only in
`tests/`, so the geometry and IFCX test crates can iterate it. Each entry is a `Fixture`:

| Field | Meaning |
|---|---|
| `id` | `F1`..`F9` for D.7; any other case is lowercase with a hyphen (`dw-l`, `dw-t`) or `S-shell`, so it never reads as a D.7 id |
| `title` | the case in a few words |
| `source` | the knowledge-base article (`KB 303968`), or the sample it comes from |
| `owner` | the key of the epic in docs/roadmap.md that owns the constructor |
| `increment` | the SRS increment whose exit needs the constructor (F1, F2, F3, F6, F7: 1; F8, F9: 2; F4, F5: 3) |
| `seeded` | whether the constructor gives the same identities on every call, so two builds compare equal |
| `build` | the constructor, `None` until the owner adds it |

Every entry with a constructor inherits the generic checks:

- `fixtures::check` (run by `cargo test -p archicraft-model --test fixtures`): no integrity
  problems, every element passes `validate_element`, every identity is unique and, when seeded,
  two builds are equal. Its error starts with the fixture id.
- `cargo test -p archicraft-geometry --test fixtures`: evaluation without problems and every
  body part closed and 2-manifold (IFX-032).
- `cargo test -p archicraft-ifcx --test fixtures`: the file saves without warnings and validates
  without problems, loads back equal (revision normalised) and save-load-save is
  byte-identical (IFX-064).

**Adding an entry.** The owner adds `pub fn f1_trapezoidal_wall() -> Project` (or similar) to
`src/fixtures.rs`, built with `samples::FixtureBuilder` like `samples.rs`, without clocks or
randomness, sets `build: Some(f1_trapezoidal_wall)` and `seeded: true` in the entry. Fixture-specific assertions (the 880/400 of F7, say)
go into `crates/archicraft-model/tests/fixtures.rs` or the owner's own tests. A new non-D.7
case gets a new `EXTRA` entry. A deliberately invalid case does not belong here; keep it in the
owner's tests.

**The increment gate.** `REQUIRED_INCREMENT` (0 today) is the increment up to which every
entry must have a constructor; `fixtures::check_increment` fails and names each fixture
without one. The verification of an increment's exit criterion raises it to that increment
(1 after increment 1, so F1, F2, F3, F6 and F7 must be built), which turns a missing
constructor into a failing test.

## Appendix D defaults

`crates/archicraft-model/tests/defaults.rs` pins the defaults of SRS Appendix D for a new
project from `default_metric_project()`, so a refactor cannot change one silently. `ROWS` has
one entry per value. Each entry's reference starts with `D.<n> <setting>:`, using the setting
name from the SRS table (`D.2 Wall: 0.25 m thick`), and every failure message starts with that
reference. Each entry is one of three kinds:

- `Checked`: a getter or a constant compared with the Appendix D value. Floats are compared
  with 1e-12; lower bounds such as "at least 100 undo steps" are compared with `>=`.
- `Elsewhere`: the value lives in another crate, and that crate's `tests/defaults.rs` pins it
  with the same reference in its assertion message. The model test checks that the file
  contains the reference. These are the D.1 view range in `crates/archicraft-geometry` and the
  preference defaults (autosave, backups, undo clamp, snap radius, angle increment) in
  `crates/archicraft-app`, which loads a temporary preferences file to run the private clamp.
- `Pending { owner }`: the value does not exist yet. `owner` names the roadmap epic that adds
  it. The test prints the pending list (`cargo test -p archicraft-model --test defaults --
  --nocapture`).

`every_appendix_d_row_is_in_the_table` reads the D.1 to D.3 tables of `docs/SRS.md` and fails
when a row has no entry. `d4_every_template_material_has_the_priority_of_its_group` maps every
template material by name to its D.4 group and checks the group priority. A material without a
group fails, and so does a mapped name that is not in the template. `d4_groups_match_the_srs_table`
keeps the group table equal to the SRS one.

To convert a pending row when the owner epic adds the value: replace
`pending OWNER` with a check closure (`|p| close(p.tool_defaults.column.width, 0.30)`), or with
`elsewhere "<crate>/tests/defaults.rs"` when the value lives outside the model crate. In the
second case, add the assertion there and repeat the reference in its message. A setting with
several values becomes one row per value, each starting with the same `D.<n> <setting>:`
prefix. Changing an Appendix D value is an SRS change: update `docs/SRS.md` and the row
together.

## Fuzzing

Every parser of external files is fuzzed with a coverage-guided fuzzer (NFR-REL-007,
NFR-SEC-003, SRS Appendix D.9). `fuzz/` holds the cargo-fuzz targets as their own Cargo
workspace: the root `Cargo.toml` excludes it, so the stable build, clippy and `cargo deny`
never see it, and only fuzzing needs a nightly toolchain.

| Target | Input | What may not happen |
|---|---|---|
| `ifcx_load` | arbitrary bytes | a panic along the application's open path: `archicraft_ifcx::load`, then `ModelGeometry::evaluate`, `save` and `load` again; a rejection without a message |
| `ifcx_validate` | arbitrary bytes | a panic in `validate::parse` or `validate::validate` |
| `units_parse` | arbitrary UTF-8 | a panic in `parse_length` (every length unit) or `parse_angle` (every angle unit) with every number format; a non-finite accepted value |

`fuzz/dict/ifcx.dict` is the libFuzzer dictionary for the IFCX targets: JSON tokens, every
object key of the golden files (IFCX structure, `bsi::`, `usd::` and `archicraft::`
attributes and their fields) and frequent values. Extend it when the format gains keys.

**Corpus.** `scripts/fuzz-corpus.sh` seeds `fuzz/corpus/<target>/` with both reference models
(written by the `reference_models` example), the golden files, every corrupt fixture of
`crates/archicraft-ifcx/tests/corrupt/` and four R2 examples (Hello Wall, the PCERT sample
scene's architecture model, Tekla House, the ACCA building), plus typed lengths and angles
for `units_parse`. The R2 examples are fetched from IFC5-development at the commit
`conformance/run.sh` pins, through the blob-filtered clone in `conformance/.ifc5`, and never
committed (NFR-LEG-003); the script keeps the list of example paths. Existing corpus entries
stay, so later runs build on earlier ones. The output (`fuzz/target/`, `fuzz/corpus/`,
`fuzz/artifacts/`, `fuzz/coverage/`) is git-ignored: `git status` is clean after a run.

**Local run.** Install the tools once, seed, then run a target for some minutes (10 when
left out):

```sh
rustup toolchain install nightly --profile minimal --component rustfmt
cargo install cargo-fuzz --version 0.13.2 --locked
scripts/fuzz-corpus.sh
scripts/fuzz-run.sh ifcx_load 10
```

`scripts/fuzz-run.sh` holds the run flags the nightly job uses too:
`-rss_limit_mb=2048 -timeout=10 -max_len=4194304`, plus `-dict=fuzz/dict/ifcx.dict` for the
IFCX targets. The limits make memory-hungry and slow inputs findings too: a crafted file that
exhausts memory or stalls the reader is a denial of service, in scope of NFR-SEC-003.
libFuzzer truncates seeds above `-max_len` (Tekla House is about 40 MB). Further libFuzzer
flags go straight to `cargo +nightly fuzz run <target> -- <flags>`.
`cargo +nightly fmt --check` in `fuzz/` checks the targets' formatting.

**Nightly job.** `.github/workflows/fuzz.yml` runs every night at 02:17 UTC on `main` with
10 minutes per target, and by hand with a duration of 1 to 100 minutes per target
(`gh workflow run fuzz.yml -f minutes=<n>`). It is the only CI job with a nightly toolchain.
It checks the formatting of `fuzz/`, restores the corpus of the newest earlier run from the
Actions cache (key prefix `fuzz-corpus-`), seeds it with `scripts/fuzz-corpus.sh`, builds the
targets (and fails when that changes `fuzz/Cargo.lock`), then runs `ifcx_load`,
`ifcx_validate` and `units_parse` one after another with `scripts/fuzz-run.sh`, within
GitHub's 6-hour job cap. Each target runs even when an earlier one found something. The
grown corpus is minimised (`cargo +nightly fuzz cmin`: one input per coverage feature,
truncated to `-max_len`) and saved under a new key, after a finding too, so the next run
starts from it. A run by hand refuses a duration outside 1 to 100 minutes.
Any crash, timeout or out-of-memory input fails the job and is uploaded as the
`fuzz-findings` artefact (the contents of `fuzz/artifacts/`, kept for 30 days); download it
with `gh run download <run id> -n fuzz-findings` and promote each input as described next.

**Promoting a finding.** A crash, timeout or out-of-memory input lands in
`fuzz/artifacts/<target>/`. Minimise it with
`cargo +nightly fuzz tmin <target> fuzz/artifacts/<target>/<file>`, fix the cause, and commit
the minimised input to `crates/archicraft-ifcx/tests/fuzz-regressions/` under a name that
says what it exercises, with the `.ifcx` extension (so `.gitattributes` keeps its bytes).
`crates/archicraft-ifcx/tests/fuzz_regressions.rs` replays every file there along the
`ifcx_load` path on stable, in the test jobs of `ci.yml` (Linux), `windows.yml` and `macos.yml`,
and fails on a file that takes longer than the fuzz runs' 10 s time-out. A time-out or
out-of-memory input is often too large to commit at the size that crosses the limit, so the
committed input is the smallest one the fix treats differently, and a test there pins what the
fix does with it (such as a slab skipped with a message);
`crates/archicraft-app/tests/ui.rs` opens every file there and every corrupt fixture through
the application and expects the load report or the "Cannot open the project" message.
The directory starts with the inputs of `malformed_input_is_rejected_without_panicking`
(tests/roundtrip.rs). A `units_parse` finding becomes a unit test in
`crates/archicraft-model/src/units.rs` instead.

**Release rule.** Before every release, each target runs for at least one hour on the seeded
corpus (D.9) without a finding: `gh workflow run fuzz.yml -f minutes=60` (about three and a
half hours in all). Findings are fixed and promoted first.

Record each release run in the table below (the release checklist links here): the date, the
commit, each target's duration, executions and coverage from libFuzzer's final statistics
(`-print_final_stats=1`: `stat::number_of_executed_units` and the last `cov:` and `ft:` values),
and the findings with their fixes. A finding is a panic, a rejection without a message, an
input that takes longer than 10 s or one that needs more than 2 GB of memory (the flags of
`scripts/fuzz-run.sh`).

The first campaign (archicraft-lnow) started with a 15-minute exploratory round of each target
in fork mode (`-fork`, findings ignored so that one does not stop the others; about 1.1 M,
1.3 M and 2.6 M executions), which found nothing, and hand-crafted inputs for the hot spots
that random mutation rarely reaches: huge slab outlines, many walls meeting at one point or
crossing, thousands of storeys, repeated `children` entries, and every number of the
ArchiCraft attributes of a golden file replaced in turn by extreme values (3,330 files). They
found four problems:

1. *Time-out:* a slab outline of 32,003 points (324 KB) took 16 s to open, because the
   self-intersection checks of `validate_ring` grow with the square of the points. Fixed:
   `MAX_SLAB_POINTS` limits a slab to 1,000 points in its outline and holes together, checked
   before those checks run; the slab is skipped with a message. Regression:
   `slab-outline-1003-points.ifcx`.
2. *Out of memory:* a storey listed 5,000 times among the building's children (260 KB) was
   read once per listing; saving the 5,000 storeys needed more than 2 GB. Fixed: the reader
   reads a storey once and reports each further listing. Regression:
   `storey-listed-three-times.ifcx`.
3. *Time-out* (found in review): a slab of 999 points listed 20,000 times among a storey's
   children (1 MB) was read and validated once per listing and took longer than 10 s. Fixed:
   the reader reads an element once and reports each further listing before reading it again.
   Regression: `slab-listed-three-times.ifcx`.
4. *Out of memory, not fixed here:* 400 valid slabs of 999 points each (3.3 MB) open with about
   300 MB, but saving them writes 52 MB of meshes and needs 2.7 GB, and reading that file
   back needs 2.8 GB. The IFCX reader and writer hold the whole file as a JSON tree; that is a
   design change, filed as archicraft-4rrc with the recipe for the input.

The final runs above used `scripts/fuzz-run.sh` on the corpus grown by the exploratory round
and earlier runs, with the regression files added, one process per target, all at once. The
units grammar changed on `main` during the campaign (archicraft-eya.1), so `units_parse` also
ran on that commit. Rebasing the fixes onto it (the model's errors had become localized
messages, archicraft-9w3.1) changed only how the slab limit is reported, so each target ran
another 10 minutes on the rebased commit. The hand-crafted inputs were not added to the
seeded corpus, and coverage was not checked with `cargo fuzz coverage`; both are
archicraft-4ehi.

## Security review

`cargo deny check advisories` checks the dependency graph against the RustSec advisory
database in CI; `deny.toml` lists each ignored advisory with its reason.

**Untrusted input (NFR-SEC-003).** Every file ArchiCraft opens is untrusted input. The IFCX
reader enforces the limits of SRS Appendix D.9, each tested at its boundary in
`crates/archicraft-ifcx/tests/limits.rs`:

- file size at most 2 GB, checked against the file's length before reading
  (`archicraft_ifcx::load_path`), and the read stops one byte past the limit, so a file that
  grows while it is read is rejected too;
- JSON nesting fewer than 128 levels in the whole document (the recursion limit of
  `serde_json`);
- `children`/`inherits` chains at most 64 deep, reported with the node path;
- at most 32 imports.

Beyond D.9, three bounds keep a small crafted file from stalling the reader or exhausting memory
(found by the first fuzz campaign, Fuzzing): a slab has at most 1,000 points in its outline
and holes together (`MAX_SLAB_POINTS` in `crates/archicraft-model/src/validate.rs`, because
the self-intersection checks grow with the square of the points), and a storey that the
building lists more than once is read once, the further listings reported, and so is an
element listed more than once in one storey or several.

**No execution.** File content only ever becomes data: the reader has no `eval`, loads no
plugins or libraries and spawns no processes, and nothing in a file selects code to run.
`deny.toml` `[bans]` guards this mechanically: it denies script engines and WebAssembly
runtimes (rhai, mlua, rlua, boa_engine, deno_core, v8, wasmtime, wasmer), and allows
`libloading` only under the graphics and windowing crates that load the system's GPU and
display libraries (ash, dlib, khronos-egl, wgpu-hal, x11rb). Adding any of them to an
ArchiCraft crate fails `cargo deny check bans` in the CI job "Licences and sources".

This property is reviewed before every release: check that the reader still holds no code
path from file content to execution, and that the bans and their reasons still apply.
